# Архитектура обработки

## 1. Сколько процессоров и по какому критерию

**Один процессор.** Критерий: число процессоров равно числу независимых
состояний, а рекомендация требует одновременного знания очередей всех станций
— состояние неделимо, поэтому процессор один.

Площадка мала: 40 машин × 4 станции ≈ килобайты состояния и ~40 сообщений/с;
один процесс справляется с запасом, а любая нарезка потребовала бы обмена
состоянием между частями.

## 2. Ключ процессора и его состояние

Ключ обработки — **`unit_uuid`**: партиционирование входа по машине сохраняет
порядок её сообщений внутри партиции, что критично для дедупликации
`ts <= last_ts` и для корректной FSM (состояния машины определяются
последовательностью её позиций).

В состоянии процессора:

| Срез | Что хранится |
|---|---|
| `unit_uuid → CarRuntime` | последняя позиция/`ts`/скорость, состояние FSM, момент входа в радиус 50 м, цель заезда (своя/рекомендованная), флаги «радиус решения пройден», «решение сделано» |
| `station → StationState` | кто и когда занял (`occupied_by`, `occupied_at`), расчётное освобождение `released_at` |
| глобальное | «сейчас» = max `ts` среди учтённых сообщений; последние опубликованные очереди станций (для диффа) |

## 3. Телеметрия по машинам, очередь по станциям, рекомендация — по всем станциям

Противоречие разрешается **единым процессом, который держит все три среза
в одной памяти**: консьюмер читает телеметрию по `unit_uuid`, движок очереди
пересчитывает срез станций из среза машин, решатель рекомендаций видит все
очереди сразу. Ключ процесса — `unit_uuid` (вход), станции — внутренняя
индексация, а не отдельная топология.

Альтернатива — шардирование по станциям с обменом «тени» очередей или
двухфазный конвейер (агрегатор очередей → решатель) — требует промежуточного
топика и синхронизации срезов, при 4 станциях не оправдана.

## 4. Партиции, реплики, предел параллелизма

| Топик | Партиции | Ключ | Почему |
|---|---|---|---|
| `telemetry.v1` | 4 | `unit_uuid` | порядок сообщений машины внутри партиции |
| `queue.v1` | 4 | `station_uuid` | порядок публикаций по станции |
| `decision.v1` | 4 | `unit_uuid` | порядок решений по машине |

Реплики: для локального запуска 1; в проде 3 при `min.insync.replicas=2`.

Предел параллелизма — **один инстанс процессора на консьюмер-группу**:
логика рекомендации глобальна, состояние не расшариваемо. Масштабирование —
вертикальное (одна группа, один подписант на все партиции). Горизонтальный
рост потребует переразбиения по независимым площадкам (группа станций со
своими машинами) — на данных ТЗ такой необходимости нет.

## 5. Гарантии доставки

**At-least-once везде, идемпотентность — контентом, транзакции не
используются.**

- Оффсет коммитится после обработки сообщения и публикации выходов; при
  падении переигрывается максимум одно сообщение (коммит после каждого
  сообщения — осознанный компромисс: ~40 коммитов/с для тестового задания
  приемлемы, при росте потока — коммит пачками).
- `queue.v1` естественно идемпотентен: очередь публикуется только при
  изменении состава/порядка/времён, повторная публикация того же состояния
  невозможна по построению диффа.
- `decision.v1` детерминирован временем событий: повторное проигрывание даст
  то же решение. Дубль при ретрае безвреден для логики, но потребитель должен
  уметь де-дуплицировать по (`unit_uuid`, `at`), если ему важна exactly-once
  семантика на своей стороне.
- Транзакционность (атомарность «очередь + решение» в одном батче) не нужна:
  это независимые события, консьюмеры независимы; цена транзакций (пид,
  координатор, задержки) не окупается. Идемпотентный продюсер librdkafka не
  используется, потому что выбран aiokafka, где его нет; `acks=all` есть.

## 6. Рестарт

- **Источник состояния — replay `telemetry.v1`.** Расчёт детерминирован
  временем событий («сейчас» = max `ts`, часы компьютера не используются),
  поэтому прогон топика с `earliest` восстанавливает состояние точно.
- Обычный рестарт: группа продолжит с закоммиченных оффсетов — состояние
  накатывается только с момента коммита; потеря in-memory состояния при
  откате оффсетов компенсируется replay (см. компромисс ниже).
- Время восстановления: длина retention × 40 msg/s; для локального запуска
  (час retention) — секунды.
- **Уже выданные решения при повторном проигрывании**: `queue.v1` придёт
  заново только для изменившихся очередей (дифф), `decision.v1` будет
  продублирован для каждого пересечения радиуса решения — потребитель
  де-дуплицирует по (`unit_uuid`, `at`). Это следствие выбранной простоты;
  устраняется компактированным state-топиком (снапшоты `CarRuntime` +
  `StationState`), который я сознательно не стал добавлять: он усложняет
  код ради рестарт-паттерна, который replay покрывает.

## 7. Что сознательно не вынесено в отдельный процессор

- **Решатель рекомендаций** — ему нужны очереди всех станций; отдельный
  процессор потребовал бы промежуточный топик и синхронизацию срезов.
- **Пересчёт и дифф-публикация очередей** — тривиальная работа на общем
  состоянии (4 станции × 40 машин, пересчёт дешевле межпроцессной передачи).
- **Генератор** — тестовый инструмент, а не часть сервиса: живёт отдельным
  процессом с собственной группой, в логику процессора не вмешивается.
