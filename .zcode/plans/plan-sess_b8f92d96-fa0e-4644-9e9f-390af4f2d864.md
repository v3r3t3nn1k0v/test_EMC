# Доработка решения ТЗ «Виртуальные очереди»

## Context

Решается тестовое задание Senior Python Engineer: сервис восстанавливает очереди на станциях по телеметрии из Kafka (`telemetry.v1`) и публикует `queue.v1`/`decision.v1`, плюс генератор телеметрии. Сейчас готово ~20%: геометрия (`geo.py` — готов), конфиг (`config.py` — почти готов), каркас моделей (`models.py`) и черновик FSM машины (`car_fsm.py`) с ошибками. Ядра задачи — движка очереди и рекомендаций, Kafka-сервиса, генератора, тестов и документации — нет.

Принятые решения: клиент **aiokafka**; локальный запуск через **docker-compose**; генератор **замыкает контур** (читает `decision.v1` и перестраивает маршруты).

Ключевой принцип: FSM, движок очереди и движок рекомендаций — чистые детерминированные функции без Kafka (ТЗ требует тестов без брокера); Kafka-слой — тонкая обвязка.

## 1. Доработка существующих модулей

### `src/vq/config.py`
- Все константы (радиусы, 230 с, 36 км/ч, пороги 30/60 с и т.д.) сделать полями `Config` с текущими значениями по умолчанию — тестам нужна кастомная геометрия площадки.

### `src/vq/models.py`
- Добавить: `QueueEntry` (unit_uuid, eta, service_start, free_at, wait_seconds), `StationState` (occupied_by, occupied_at, released_at), `Decision` (result, from/to, gain | reason).
- В `CarRuntime` добавить `entered_radius_at` (момент входа в 50 м целевой станции) — под правило «приезд ждущей = момент входа в радиус».

### `src/vq/car_fsm.py`
1. **Фикс-бага:** все проверки расстояний вести по **целевой станции** (`recommended_station ?? own_station`) — иначе перенаправленная машина никогда не займёт станцию.
2. Эмитить `OCCUPIED` (первое сообщение «на станции», станция свободна по расчётному расписанию), `RELEASED` (занявшая машина вышла из радиуса), `CROSSED_DECISION_RADIUS` (впервые < 1500 м к своей станции, только когда едет к своей и решения в этом заезде ещё не было).
3. Отслеживать `entered_radius_at` при входе в 50 м целевой станции.
4. Сброс per-заезд флагов (`decision_made`, `recommended_station`, `was_within_decision_radius`) при переходе `TO_UNLOAD → TO_STATION` (новый заезд начинается к своей станции).
5. `stale` сравнивать с `cfg.fresh_telemetry_s`, убрать захардкоженное 30; подчистить мёртвый код и опечатки.

### `src/vq/geo.py` — без изменений.

## 2. Новые модули: ядро расчёта (без брокера)

### `src/vq/queue_engine.py`
- **Занятие/освобождение:** станция занята в момент первого сообщения «на станции» при свободной станции; освобождение — min(занятие + 230, выход занявшей машины из радиуса). Занявшую машину не исключать из очереди как протухшую.
- **`build_queue(station, cars, now)`:** занявшая машина первой (`free_at = занятие + 230`); остальные — по ETA (TO_STATION: dist/10 м/с; TO_UNLOAD: (dist до разгрузки + разгрузка→станция)/10; ждущая в радиусе: `entered_radius_at`), сортировка по приезду, последовательная симуляция по 230 с (`service_start = max(приезд, free_at предыдущей)`), горизонт 30 мин, отсев машин с позицией старше 30 с. ETA=null только у занявшей.

### `src/vq/decision.py`
- На `CROSSED_DECISION_RADIUS`: ожидание по каждой станции = max(0, `free_at` последней машины очереди, приедущей раньше нашей, − наш приезд; нет таких — 0).
- Выбор: минимум ожидания; при равенстве — своя станция, затем ближайшая. Выигрыш < 60 с → `rejected/no_gain`; сообщение старше «сейчас» на > 30 с → `rejected/stale_telemetry`.
- При `recommended`: целевая станция машины меняется, она уходит из очереди своей станции в очередь рекомендованной.

## 3. Kafka-слой (aiokafka)

### `src/vq/serde.py`
Парсинг `telemetry.v1`, сериализация `queue.v1`/`decision.v1`; время — ISO 8601 UTC с `Z`; `at` = «сейчас» = max `ts` среди учтённых сообщений.

### `src/vq/service.py`
- Консюмер `telemetry.v1` (группа `vq-processor`), состояние в памяти: 40 `CarRuntime` + 4 `StationState` + «сейчас».
- На каждое учтённое сообщение: FSM → пересчёт всех 4 очередей → дифф с предыдущими → публикация изменившихся в `queue.v1` (ключ `station_uuid`); на пересечение 1500 м → расчёт → публикация в `decision.v1` (ключ `unit_uuid`).
- Коммит оффсетов после обработки пачки; at-least-once.

### `src/vq/generator.py` (замкнутый контур)
- Симулятор 40 машин: прямые станция↔разгрузка, 10 м/с ± шум, соблюдение очереди (занята — стоит в радиусе), 200 с обслуживание + 30 с манёвр; 1 сообщение/с на машину, темп реальный или с ускорением (флаг).
- Дубли (вероятность) и опоздания до 60 с (пересортировка исходящего буфера).
- Консюмер `decision.v1`: при `recommended` машина перестраивается на рекомендованную станцию с текущей позиции; после обслуживания и разгрузки возвращается к своей.

## 4. Тесты (`tests/`, pytest, брокер не нужен)

- `test_car_fsm.py`: определение всех состояний, дефолт для первого сообщения, дубли и не-по-порядку (`ts <= last_ts` игнор, опоздавшее с новым `ts` учитывается), вход/выход радиуса, пересечение 1500 м, сброс флагов на новый заезд, целевая станция после рекомендации.
- `test_queue_engine.py`: **пример из ТЗ воспроизводится точно** (T1/T2/T3 → 12:02:50 / 12:06:40 / 12:10:30, ожидания 0/50/100); досрочное освобождение при выходе из радиуса; горизонт 30 мин; отсев протухших; «приезд = момент входа в радиус».
- `test_decision.py`: **пример T4** → `recommended`, S1→S2, gain 80; `no_gain`; `stale_telemetry`; равенство → своя станция; перенаправление исключает машину из очереди своей станции; вторая рекомендация только после станции.
- `test_serde.py`: форматы JSON/ISO 8601.

## 5. Инфраструктура и документация

- `pyproject.toml` (aiokafka, pytest; пакет `vq` из `src/`), `src/vq/__init__.py`.
- `docker-compose.yml`: Kafka (single-node KRaft) + `vq-service` + `vq-generator`; `Dockerfile`.
- `README.md`: команды запуска и тестов, решения по неоднозначностям ТЗ (какая станция считается целевой после рекомендации, «свободна ли станция» по расчётному расписанию и т.п.), что сознательно не сделано, время.
- `ARCHITECTURE.md` (1–2 стр., по 7 пунктам ТЗ): один процессор (состояние 40 машин + 4 станции помещается в память, рекомендация требует очередей всех станций — шардирование по станциям невозможно без обмена состоянием); ключ процессора `unit_uuid`, в состоянии — машины и станции; партиции: `telemetry.v1` 4 (ключ `unit_uuid`), `queue.v1` 4 (`station_uuid`), `decision.v1` 4 (`unit_uuid`); параллелизм ограничен одним инстансом процессора; гарантии: at-least-once + идемпотентность (неизменные очереди не публикуются, решения детерминированы во времени событий), транзакции не нужны; рестарт: состояние из памяти + committed offsets, повторное проигрывание повторно эмитит решения (описать, вариант улучшения — compacted state-топик); генератор не вынесен в процессор, т.к. это тестовый инструмент.

## Порядок работы

1. Скелет проекта (pyproject, `__init__.py`, тестовая фикстура площадки с удобной геометрией).
2. Доработка `config.py` → `models.py` → `car_fsm.py` (+ их тесты).
3. `queue_engine.py` + тесты (пример ТЗ — сразу).
4. `decision.py` + тесты (пример T4).
5. `serde.py` → `service.py` → `generator.py`.
6. docker-compose, README, ARCHITECTURE.

## Проверка

- `pytest -q` — всё зелёное, оба примера из ТЗ воспроизведены тестами до буквы.
- `docker compose up` — генератор пишет телеметрию, сервис публикует `queue.v1`/`decision.v1`; консьюмером топиков убедиться: очереди меняются при событиях, одинаковые подряд не публикуются, при перенаправлении видно `decision.v1` и перетасовку очередей.
