# Виртуальные очереди

Сервис восстанавливает очереди самосвалов на станциях по одной лишь телеметрии
(позиция + скорость, раз в секунду) и рекомендует машине другую станцию, если
там примут заметно раньше. Расчёт полностью ведётся во времени событий —
записанный поток можно прогнать с ускорением и получить тот же результат.

- Вход: Kafka-топик `telemetry.v1` (ключ `unit_uuid`), 1 сообщение/с на машину.
- Выход: `queue.v1` (ключ `station_uuid`) — при каждом изменении очереди станции;
  `decision.v1` (ключ `unit_uuid`) — решение для машины, пересёкшей радиус
  решения 1500 м, включая отказы `no_gain` / `stale_telemetry`.
- Генератор телеметрии: симулятор площадки (40 машин, 4 станции, разгрузка) с
  очередями, дублями и опозданиями до 60 с; читает `decision.v1` и
  перенаправляет машины — контур замкнут.

## Запуск

```bash
docker compose up --build          
```

Наблюдать за топиками (в отдельных терминалах):

```bash
docker compose run --rm watch-queue       # очередь к станции
docker compose run --rm watch-decisions   # рекомендации
docker compose run --rm watch-telemetry   # входная телеметрия
```

Брокер доступен с хоста на `localhost:29092`.

Без Docker (брокер уже поднят, например Redpanda):

```bash
python -m pip install -e .
KAFKA_BOOTSTRAP_SERVERS=localhost:29092 python -m vq.service &
KAFKA_BOOTSTRAP_SERVERS=localhost:29092 python -m vq.generator
```

Настройки — только env:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `KAFKA_BOOTSTRAP_SERVERS` | `localhost:9092` | брокер |
| `TELEMETRY_TOPIC` / `QUEUE_TOPIC` / `DECISION_TOPIC` | `telemetry.v1` / `queue.v1` / `decision.v1` | топики |
| `CONSUMER_GROUP` | `vq-processor` / `vq-generator` | консьюмер-группа |
| `GEN_SPEEDUP` | `10` | ускорение времени генератора (1 — реальный темп) |
| `GEN_LATE_MAX_S` | `60` | максимум опоздания сообщений, с |
| `GEN_DUPLICATE_PROB` | `0.005` | вероятность дубля на сообщение |
| `GEN_SEED` / `GEN_WARMUP` | `42` / `600` | воспроизводимость и прогрев симуляции |

## Тесты

Расчёт проверяется без брокера (требование ТЗ), 56 тестов:

```bash
python -m pip install -e ".[dev]"
python -m pytest
```

Оба примера из ТЗ воспроизведены буквально: очередь S1 из T1/T2/T3
(12:02:50 / 12:06:40 / 12:10:30, ожидания 0/50/100) и рекомендация T4 → S2
с выигрышем 80 с. Есть сквозной тест без брокера: телеметрия генератора
прогоняется через процессор с ручным замыканием контура решений, занятость
станций и состав ожидания совпадают с «правдой» симулятора.

## Устройство

```
src/vq/
  config.py      площадка и все константы  — поля Config
  geo.py         haversine, расчёт времени в пути
  models.py      Telemetry, CarRuntime, StationState, QueueEntry/StationQueue, Decision
  car_fsm.py     FSM машины: таблица состояний + сигналы (вход/выход радиусов станции ,
                 пересечение 1500 м, новый заезд) — чистая функция без Kafka
  queue_engine.py занятие/освобождение станции (во времени события) и
                 чистый расчёт очереди на 30 минут
  decision.py    решатель рекомендаций: ожидание на каждой станции, выбор,
                 no_gain / stale_telemetry, переключение цели заезда
  serde.py       сериализация в JSON
  service.py     процессор: consume → расчёт → produce; дифф-публикация очередей
  generator.py   симулятор площадки, дубли/опоздания, замкнутый контур
```

Архитектура потоков — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Решения по неоднозначностям ТЗ

ТЗ разрешает принимать решения самостоятельно — все принятые зафиксированы
здесь и подтверждены тестами.

1. **Целевая станция.** Все проверки радиусов для машины ведутся относительно
   *целевой* станции заезда: рекомендованной, если рекомендация принята, иначе
   своей. После обслуживания на рекомендованной и разгрузки заезд начинается
   заново — к своей.
2. **Переходы по радиусам — по пересечению границы (гистерезис).** «На станции»
   держится, пока машина в радиусе 50 м, даже если скорость уже больше порога
   (манёвр); «к станции» машина переходит, только побывав в радиусе разгрузки
   и выйдя из него — иначе машина в 100 м от станции сразу считалась бы
   «к станции».
3. **Занятие станции.** Занятие — факт станции, не машины: срабатывает на любом
   учтённом сообщении «на станции», когда станция свободна по расписанию (не
   только на первое вхождение в состояние — станция могла освободиться, когда
   машина уже стояла и ждала). Освобождение — занятие + 230 с либо выход
   занявшей машины из радиуса, что раньше.
4. **Отслужившая машина, оставшаяся стоять в радиусе**, не занимается повторно
   («первое сообщение» уже было) и в очередь не попадает; признак — заполненный
   `station_occupied_at`.
5. **`eta` в очереди.** `null` — только у обслуживаемой (занявшей) машины;
   у ждущей в радиусе `eta` = момент входа в радиус (приезд уже наступил),
   благодаря этому `wait_seconds` осмыслен для всех.
6. **Ничья при выборе станции:** своя станция, затем ближайшая. Ничья двух
   свободных чужих станций разрешается ближней.
7. **Порядок проверки отказов:** `stale_telemetry` проверяется до расчёта —
   протухшее сообщение обесценивает сравнение станций.
8. **Опоздавшее сообщение** с новым `ts` учитывается, но если оно старше
   «сейчас» на 30 с: рекомендация по нему отклоняется как `stale_telemetry`
   (расчёт за заезд при этом считается состоявшимся — пересечение было), а
   сама машина исключается из очереди до появления свежей позиции.
9. **Дифф-публикация очередей:** сравнивается состав/порядок/времена строк;
   момент расчёта `at` в диффе не участвует, иначе каждая секунда «сейчас»
   порождала бы публикацию. Пустая очередь — стартовое состояние станции и
   отдельно не публикуется.
10. **Одновременное прибытие двух машин** на освободившуюся станцию: займёт
    та, чьё сообщение обработано раньше (порядок Kafka); при равном ETA в
    очереди детерминированный порядок по `unit_uuid`.
11. **Дедупликация** строго по правилу  *плавно*: порядок сообщений одной
    машины сохраняется и не убивается дедупликацией, а общий поток
    не отсортирован по времени.

## Что сознательно не сделано

- **Персистентное состояние.** Состояние процессора в памяти; рестарт —
  продолжение с закоммиченных оффсетов или полный replay топика (расчёт
  детерминирован временем событий). Компактированный state-топик — очевидное
  улучшение, не оправданное объёмом тестового задания (см. ARCHITECTURE.md).
- **Горизонтальное масштабирование.** Один процессор: рекомендация требует
    очередей всех станций 
- **Идемпотентный продюсер Kafka** не используется — aiokafka его не
  поддерживает; идемпотентность достигается контентом
- **Реализм генератора** ограничен: нет поломок, обгонов, GPS-шума; опоздания
  до 60 с и дубли есть.
